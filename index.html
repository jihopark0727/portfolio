01 Problem

읽고, 분류하고, 옮겨 적는 사이에
요청이 사라집니다

기획팀은 외부 거래처에서 하루에도 여러 건의 요청 메일을 받습니다. 사람이 직접 읽고, 분류하고, Jira 티켓으로 옮겨 적는 방식이었고 그 과정에서 누락, 중복, 형식 불일치가 반복됐습니다. 들여다보니 낭비는 두 방향으로 생기고 있었습니다.

필요 없는 절차

팀 안에서 끝나는 업무까지 매번 티켓이 된다

다른 팀과 협업할 일이 없는 업무에도 티켓 절차가 붙었습니다.

빠지는 절차

정작 협업이 필요한 요청은 조용히 묻힌다

다른 팀의 손이 필요한 요청이 처리 경로에 오르지 못했습니다.

02 Principle

원칙은 하나, 누락 0을 목표로

프로젝트 전체를 누락 0을 목표로 한 설계 원칙 하나로 묶었습니다. 어떤 실패 경로도 조용히 버리지 않는다. 무엇이 실패하든 반드시 사람에게 확인요망 알림이 가도록 모든 예외 처리를 설계했습니다.

›티켓 생성이 실패하면 사람에게 확인요망 알림
›LLM 분석이 실패하면 사람에게 확인요망 알림
›초안이 유실되면 사람에게 확인요망 알림

이 원칙이 이후 모든 기능 결정의 기준이 됐습니다. 버튼을 조건에 따라 숨기지 않고, 자동 판단만으로 카드를 취소하지 않는 것이 그 예입니다.

03 Flow

메일 수신부터 티켓까지, 한 흐름으로

사람이 읽고 분류하고 옮겨 적던 일을 다섯 단계의 흐름으로 바꿨습니다. 마지막 결정은 사람이 합니다.

01

메일 수신

Gmail API로 요청 메일을 자동 수집합니다.

02

분석

LLM이 메일의 의도와 신뢰도를 판단하고, 규칙 기반 필터가 기준점 역할을 합니다.

03

Slack 카드

정리된 요청이 채널에 카드로 올라옵니다.

04

담당자 지정

초안 카드에는 담당자 드롭다운과 [무시] 버튼만 보입니다. 처리할 필요가 없는 메일은 여기서 [무시]로 종결하고, 나머지는 드롭다운에서 담당자를 고릅니다.

05

사람이 결정

담당자가 지정되면 처리 버튼이 나타나고, 그중 하나를 누릅니다. 버튼은 AI 판단과 상관없이 항상 보입니다.

초안 단계

무시

처리할 필요가 없는 메일을 담당자 지정 없이 종결.

담당자 지정 후

완료 처리

기획팀 안에서 끝나는 업무. 기존 프로젝트에 연결한 건의 마무리도 이 버튼으로 합니다.

담당자 지정 후

티켓 생성

다른 팀과 협업이 필요한 요청을 Jira로 등록.

담당자 지정 후

기존 프로젝트 연결

다른 팀이 쓰는 기존 칸반 프로젝트의 이슈에 메일을 연결.

담당자 지정 후

원문 보기

정리된 카드와 함께 메일 원문을 확인.

담당자 지정 후

취소

종결이 아니라 담당자 지정만 취소하고 초안으로 되돌립니다.

04 AI & Human

AI는 분석하고, 결정은 사람이 합니다

AI를 업무에 붙일 때 어려웠던 부분은 어디까지 AI에 맡기고 어디부터 AI의 판단을 그대로 믿으면 안 되는지 가르는 일이었습니다.

›LLM의 역할은 메일의 의도(요청, 대화, 후속 질문 등)와 신뢰도 판단까지입니다.
›규칙 기반 필터를 기준점으로 남겨, LLM이 틀려도 파이프라인 전체가 흔들리지 않게 했습니다.
›처리 버튼은 항상 노출됩니다. 자동 판단 때문에 처리 경로가 사라지는 일을 구조적으로 막았습니다.
›결정 로그와 리포트로 봇의 판단과 사람의 최종 결정을 대조해, 분류 정확도를 수치로 재고 프롬프트를 계속 고칠 수 있는 구조를 갖췄습니다.

쓰면서 여덟 번 고쳤습니다

처음 설계가 그대로 남은 곳은 많지 않습니다. 실제 사용에서 확인한 사실과 팀원 피드백에 맞춰 흐름과 구조, 운영 환경까지 바꿨습니다.

경합

저장 직전 재조회 후 병합

백그라운드 이미지 업로드가 낡은 데이터로 저장소를 덮어써, 방금 저장된 담당자 지정 정보가 지워졌습니다. 저장 직전에 최신 상태를 다시 조회해 병합하도록 고쳤습니다.

손상

원자적 쓰기로 통일

파일을 쓰는 도중 프로세스가 죽으면 데이터가 손상됐습니다. 모든 저장을 임시 파일에 쓴 뒤 rename하는 방식으로 통일했습니다.

알림 피로 → 하루 세 번 목록 알림
처음
카드마다 스레드에 개별 리마인더를 달았습니다(업무시간 2시간 뒤, 24시간 뒤).
발견
팀원에게서 "알림이 너무 많다"는 피드백을 받았습니다.
변경
평일 09:30, 13:30, 17:00(한국시간)에 아직 처리되지 않은 카드를 채널 메시지 한 건으로 모아 알리도록 바꿨습니다. 담당자 미지정 건은 팀 전체에, 처리 중인 건은 담당자별로 묶어 해당 담당자만 멘션하고, 카드 바로가기 링크와 경과 시간을 함께 보여 줍니다.
기준
무시·완료된 건과 올라온 지 1시간이 안 된 카드는 제외합니다. 건수가 많으면 오래된 순으로 30건만 보여 주고, 대기 건이 없으면 보내지 않습니다.
안전장치
마지막 발송 회차를 저장해 재시작해도 중복 발송이 없습니다. 발송에 실패하면 조용히 버리지 않고 다음 폴링에서 다시 시도해, 누락 0 원칙을 알림에도 그대로 적용했습니다.
기존 프로젝트 연결
배경
다른 팀이 쓰는 기존 칸반 프로젝트는 필드 체계가 확정되지 않아, 봇이 티켓을 새로 만들면 잘못된 값으로 생성될 위험이 있었습니다.
설계
그래서 티켓을 새로 만들지 않고 이미 있는 이슈에 메일을 연결만 하도록 했습니다. 연결은 종결이 아니므로, 마무리는 기존 [완료 처리]를 재사용했습니다.
안전장치
번호 오타로 전혀 다른 이슈에 붙는 사고를 막기 위해, 번호를 입력하면 그 이슈의 제목을 보여 주는 확인 팝업을 한 번 더 거치게 했습니다.
변경
처음에는 채널에 확인 메시지를 새로 띄웠지만, "새 메시지로 확인시키지 말아 달라"는 피드백을 받아 팝업 안에서 처리하도록 바꿨습니다. 이 과정에서 확인 후 팝업이 닫히지 않는 문제를 찾아 고쳤고, 그 사이 담당자 지정이 취소되는 경합도 막았습니다.
운영 전환: 개인 PC에서 AWS 서버로
처음
개인 PC에서 구동해, PC가 꺼지면 봇도 멈췄습니다.
변경
AWS 서버(EC2)로 옮기고 systemd에 등록해 24시간 상시 가동하고, 장애가 나면 자동으로 재기동되게 했습니다.
분리
개발과 운영의 Slack 앱, Jira 프로젝트, 데이터 파일까지 분리해 개발 중 테스트가 운영에 섞이지 않게 했습니다.
전환
같은 Slack 앱 토큰으로 두 인스턴스가 동시에 돌면 클릭 이벤트가 갈라지기 때문에, 기존 구동을 먼저 멈춘 뒤 새 서버로 전환했습니다.
06 Troubleshooting

원인을 다 알지 못해도, 위험은 줄일 수 있습니다

간헐적으로 초안이 유실된 것처럼 보이는 버그
증상
정상적인 초안이 간헐적으로 사라진 것처럼 보였습니다. 파일 재읽기, 재시도 로직 같은 방어 코드를 여러 번 넣었지만 재현될 때마다 그 코드가 실행된 흔적이 전혀 없었습니다.
판단
애플리케이션 로직의 문제가 아닐 가능성이 높다고 봤습니다. 원인이 불확실한 상태에서 방어 코드를 계속 쌓는 것은 답이 아니었습니다.
조치
문제가 생기는 경로 자체를 줄였습니다. 종결 상태를 거쳐 되돌아오던 '담당자 지정 취소'를 하나의 동작으로 다시 구성했습니다.
원인을 끝까지 확정하지 못했더라도, 실질적인 위험을 낮추는 쪽을 택했습니다.
07 Results, Learnings

결과와 배운 것

✓테스트 512개와 typecheck가 모두 통과한 상태로 운영에 반영
✓코드 리뷰에서 나온 잠재 결함(설정이 누락되면 전체 기능이 멈출 가능성 등)을 방어 로직으로 미리 보완
✓팀 안에서 끝나는 업무와 협업이 필요한 업무를 분리해, 불필요한 티켓 생성을 줄이고 협업이 필요한 요청의 처리 경로를 보장
✓AWS 서버(EC2)에서 24시간 상시 가동하고, 장애가 나면 자동으로 재기동
✓목록 알림과 기존 프로젝트 연결의 확인 방식처럼, 팀원 피드백에서 나온 불편을 바로 구조에 반영하며 지금도 계속 개선하고 있습니다

01 Background

메일로 오는 일 말고, 요일마다 돌아오는 일이 있습니다

01 Overview

"자리 있을까?"를 감이 아니라 데이터로

카공족·노트북족·모임 등으로 카페 수요는 늘었지만, 빈 좌석을 미리 확인할 방법은 여전히 부족합니다. 자리를 찾아 매장을 한 바퀴 돌거나, 자리가 없어 발길을 돌린 경험은 누구에게나 있습니다.

주차(카카오T)·웨이팅(캐치테이블)처럼 혼잡도는 이미 하나의 정보가 되었지만, 카페는 이 흐름에서 소외돼 있었습니다. 기존 서비스는 사용자 후기 기반이라 즉각적인 변화에 대응하기 어렵고 주관이 개입돼 정확도가 떨어졌습니다. Seatify는 이 한계를 AI 이미지 분석으로 보완합니다 — 천장 CCTV 영상을 YOLO로 분석하고 Homography로 평면 투영해, "진짜" 비어 있는 좌석을 실시간으로 보여줍니다.

3초마다 특정 좌석을 조회 → 데이터가 쌓일수록 풀 스캔 비용이 실시간성을 위협. (cafe_id, seat_number) 복합 인덱스를 추가해 인덱스 레인지 스캔으로 전환, EXPLAIN으로 검증했습니다.

-- 10,000건 더미 데이터 기준 Full Scan → Index Scan 0.0044s → 0.00097s (≈4.6×)
Case 02 · 실시간 처리 개선

Cold Start 구조는 매 요청마다 YOLO 모델을 새로 로드 → I/O·초기화 비용이 반복되고 병렬 요청 시 지연. Persistent 모델 구조로 전환해 서버 기동 시 한 번만 로드하고 이후엔 추론만 수행하도록 개선했습니다.

-- 평균 응답 속도 15s → 7s (≈53% 개선)

이 외에도 시간대별 좌석 혼잡도 예측, 타 카페 추천 기능을 백엔드에 추가했고, 클릭 로그 기반 실시간 추천(Kafka 비동기 파이프라인, "현재 이 카페를 N명이 보는 중")의 설계에도 참여했습니다. 동시성 충돌을 피하는 lock-free 비동기 흐름을 목표로 했습니다.

3인 팀에서 백엔드 전반을 단독으로 담당했습니다. API 서버 설계·구현부터 인증, 파일 처리, DB, AI 연동, PDF 변환까지 서버 사이드 전체를 책임졌습니다. 무엇을 만들지는 현장 인터뷰에서 도출한 요구사항이 정했습니다.

01

RESTful API · 계층형 아키텍처

Controller → Service → Repository로 관심사를 분리하고 DTO/Entity 변환을 일관 적용. 대시보드 API는 countEmotions() · findMostFrequentEmotion() 으로 감정 통계를 집계해 시각화 데이터를 반환.

02

인증 · 파일 업로드

JWT 기반 stateless 인증으로 요청별 신원 검증. Multer로 녹음 파일을 저장하되 타임스탬프를 붙여 파일명 충돌을 방지.

03

감정 분석 파이프라인 연동

STT → 감정 분류 → 요약의 파이프라인을 백엔드에서 단계별로 연동·처리. DB는 7개 테이블로 정규화하고, 감정 결과를 세션·문장 단위로 저장해 파도/레이더 시각화에 재사용.

핵심 판단 · KoBERT → OpenAI API 전환
문제
Naver Clova STT + KoBERT 조합으로 감정 분류를 시도했으나, 긴 문장·복잡한 문맥에서 정확도가 낮고 재학습·튜닝에 과도한 리소스가 필요했습니다.
해결
감정 분석·요약을 OpenAI API로 전환. 별도 학습 없이 즉시 적용 가능하고, 복잡한 문맥에서도 감정 분류와 요약을 동시에 높은 정확도로 수행하도록 개선했습니다.
결과
STT 데이터를 더 신뢰성 있게 분석·활용 → 감정 분석 정확도와 처리 효율을 모두 향상.
'모델이 좋다'가 아니라 '우리 데이터에서 잘 동작하는가' — 검증을 기준으로 삼은 기술 의사결정이었습니다.
